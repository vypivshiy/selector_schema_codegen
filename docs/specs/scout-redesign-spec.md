# Spec: Scout HTML Context Distillation & Reconnaissance Redesign

## Problem Statement

When authoring an HTML schema or a Raw schema in KDL Schema DSL (v2.1), developers and LLM agents must inspect raw HTML pages that are often 50 KB to 2 MB in size and dominated by structural noise: inline SVGs, stylesheets, tracking scripts, navigation mega-menus, deeply nested layout wrappers, utility class soup (Tailwind/Bootstrap), and autogenerated CSS-in-JS hashes.

The current experimental HTML reconnaissance command (`ssc-gen scout`) fails to serve as a practical context generator for LLM-assisted schema authoring:

1. **Destruction of DOM Hierarchy**: Its overview mode (`--discover`) outputs flat frequency tables (`tag_stats`, `class_stats`, `id_stats`) and unranked sibling groups that strip away document hierarchy, leaving the LLM unable to see relative field paths or semantic page regions.
2. **Broken Heuristic Selector Synthesis**: The short-selector builder discards any CSS class occurring more than 5 times in the document (`RARE_CLASS_MAX = 5`). In any list of 6 or more product cards (`<div class="product-card">`), the item's own class is stripped, producing overly broad selectors (`#catalog > div`), while the fallback emits fragile root-to-leaf chains with `:nth-of-type(1)` that select only a single element instead of the repeating list. Emitted selectors are never verified against the parsed DOM tree.
3. **Rigid Grouping and Naive Ranking**: Repeating containers are grouped by exact `(tag, frozenset(classes))` identity and sorted purely by `(-count, depth)`. If the first card in a list has a state modifier (`class="card featured"`), it is excluded from the group; meanwhile, 40-item header/footer navigation lists outrank 12-item data-rich product grids.
4. **Collapsed Same-Tag Siblings Inside Cards**: When a repeating card contains multiple fields using the same tag and class (such as three `<span class="spec">` elements for year, engine, and transmission), they are merged into a single entry (`max_per_item=3`) showing samples only from the first position, hiding the remaining fields from the LLM.
5. **Shallow and Fragile Embedded JSON Discovery**: Script scanning stops at the first variable assignment per `<script>`, fails on trailing semicolons or `JSON.parse("...")` wrappers because it calls `json.loads` on unparsed tails instead of streaming `raw_decode`, and only inspects top-level keys rather than locating deeply nested data arrays and their GJSON path expressions.
6. **Missing Key-Value and Detail-Page Signals**: Non-`<table>` key-value specifications (`<dl><dt>/<dd>` and two-column label-value `<div>`/`<li>` rows) and single-item detail containers are not surfaced with ready-to-use `@rows`, `@match`, and `@value` selectors.
7. **Fragmented Manual Navigation**: Query mode forces users and agents to manually guess `--up`, `--down`, `--next`, and `--prev` steps across multiple CLI round-trips, while `--text` only inspects direct text nodes and misses text split across inline tags.

## Solution

Redesign `ssc-gen scout` from the ground up into a unified, single-call HTML context distillation and structural reconnaissance engine tailored for LLM and human KDL schema authoring (breaking backward compatibility with the legacy experimental output and CLI flags):

1. **Unified Overview-by-Default & Auto-Zoom Workflow**:
   - Running `ssc-gen scout` with no filter flags performs full-page structural distillation (retaining `--discover` as a silent deprecated no-op alias).
   - Passing filter flags (`--css`, `--text`, `--attr`, `--tag`, with `-I`/`--ignore-case` and `-F`/`--fixed`) switches into **Zoom-in Mode**: the engine finds the deepest minimal DOM nodes matching the query (including normalized text spanning inline tags), automatically climbs to their enclosing repeating list, table, or semantic container, and renders a detailed structural skeleton of that container with `<-- MATCH` annotations on the matched fields.
   - Remove low-level manual navigation and pagination flags (`--up`, `--down`, `--next`, `--prev`, `--fields`, `--offset`, `--limit`, `--snippet`, `--invert`, `--count`) in favor of automatic container expansion and a single `--full` flag that lifts default compression limits.
2. **DOM Pruning, Class Classification, and DOM-Verified Selector Synthesis**:
   - Strip technical noise (`<svg>`, `<style>`, `<noscript>`, comments, and empty layout wrappers lacking text or target attributes).
   - Classify CSS classes to filter out utility tokens (Tailwind/Bootstrap layout/spacing/color utilities, transient state modifiers like `active`/`hover`/`odd`/`even`) and autogenerated CSS-in-JS hashes (`css-*`, `sc-*`, `svelte-*`). Prioritize semantic classes whose document frequency correlates with the container's item count, alongside `id`, `data-*`, `itemprop`, `aria-*`, `name`, and `role` attributes.
   - Verify every synthesized container and relative field CSS selector against the parsed DOM tree (`soup.select`) to guarantee exact target cardinality.
3. **Three Specialized Reconnaissance Engines & Hybrid Output**:
   - **Embedded JSON Engine (`=== EMBEDDED JSON ===`)**: Scans all `<script>` tags (`application/ld+json`, `application/json`, all `var`/`let`/`const`/`window` assignments, `.push({...})` calls, and unescaped `JSON.parse("...")` payloads) plus JSON-bearing HTML attributes using standard library `json.JSONDecoder().raw_decode()` in a loop (ensuring 100% compatibility with runtime `jsonify` and generated JSON projectors without external C dependencies). Filters out trivial objects ($<2$ keys and no nested arrays), recursively discovers data-rich object arrays and dictionaries at any depth, and emits the KDL extraction pipeline hint, GJSON path expression (`path="..."`), collection size, field schema with inferred types, and sample values.
   - **Key-Value & Table Engine (`=== KEY-VALUE & TABLES ===`)**: Detects data tables (`<table>` with horizontal `<th>` headers vs vertical key-value rows), definition lists (`<dl>/<dt>/<dd>`), and repeating two-column `<div>`/`<li>` label-value rows (where the left element holds a short, row-unique label and the right element holds a varying value). Outputs verified `container`, `rows`, `key`, and `value` CSS selectors and discovered keys with sample values for `(table)struct` and `(dict)struct` authoring.
   - **Repeating Lists & Folded DOM Skeleton Engine (`=== REPEATING LISTS & DOM SKELETON ===`)**:
     - Clusters sibling elements by tag name plus shared semantic classes or child-tag structural similarity ($\text{Jaccard} \ge 0.5$), isolating one-off sibling insertions (such as ad banners) as `outlier` annotations rather than breaking the list.
     - Ranks repeating lists by information density (unique descendant fields, text entropy, and non-navigation bonuses) and collapses navigation lists (`<nav>`, `<header>`, `<footer>`, or single-link `<a>` lists) into a single summary line.
     - Merges items of each top repeating list into a unified **Union Archetype**: drops empty layout wrappers, collapses single-child chains inline via ` > `, reports verified relative CSS selectors, tracks field presence ratios (`[24/24]` vs `[5/24, optional]` as a direct signal for `fallback #null`), and disambiguates same-tag siblings within a card into either distinct `:nth-of-type(k)` positional slots (when slot counts are stable) or nested `css-all` array fields (`[array min..max items]`).
4. **Token-Efficient Default Text Digest & Structured JSON Serialization**:
   - Default `-f text` output renders a compact, LLM-optimized structural digest (`~2–3K` tokens under default limits), while `-f json` serializes the exact same structured representation.

## User Stories

1. As an LLM agent authoring an HTML schema, I want `ssc-gen scout -i page.html` to produce a complete structural digest by default without requiring `--discover`, so that my first command immediately yields actionable context.
2. As an existing automation caller, I want `--discover` to remain accepted as a silent no-op flag on `ssc-gen scout`, so that existing agent prompts and scripts invoking `ssc-gen scout --discover` continue to work without CLI errors.
3. As an LLM agent, I want `<svg>`, `<style>`, `<noscript>`, HTML comments, and empty wrapper tags stripped before analysis, so that my context window is not polluted by non-data markup.
4. As an HTML schema author working on Tailwind or CSS-in-JS sites, I want utility classes (`flex`, `px-4`, `text-gray-900`, `col-md-6`), state classes (`active`, `odd`, `even`), and hashed classes (`sc-*`, `css-*`) filtered out during selector synthesis, so that generated `.kdl` schemas rely on stable semantic selectors.
5. As an HTML schema author, I want every container and field CSS selector reported by `scout` to be verified against the live DOM tree, so that copying a selector into `css` or `css-all` in a `.kdl` pipeline is guaranteed to match the expected elements.
6. As an HTML schema author scraping product catalogs, I want repeating item classes (such as `.product-card` appearing 24 times) preserved in the synthesized `selector` rather than discarded by a low rarity cap, so that `@split-doc { css-all "..." }` selects the exact item cards.
7. As an HTML schema author, I want sibling elements in a list grouped even when one or more items carry extra modifier classes (such as `class="card featured"` or `class="row active"`), so that all items in the visual list are counted and analyzed together.
8. As an HTML schema author, I want structurally similar sibling elements without classes grouped when their descendant tag sets have a Jaccard similarity of at least 0.5, so that classless semantic HTML lists and table rows are still discovered.
9. As an HTML schema author, I want isolated non-matching elements inside a repeating container (such as a single `<div class="ad-banner">` among 20 product cards) isolated and reported as an outlier annotation, so that an inline ad does not split or corrupt the product card archetype.
10. As an LLM agent, I want repeating containers ranked by information density (number of distinct data fields, text variety, and semantic depth) rather than raw element count alone, so that a 12-item product grid ranks above a 50-item footer link list.
11. As an LLM agent, I want navigation lists (`<nav>`, `<header>`, `<footer>`, or repeating items consisting solely of a single `<a>` link) collapsed into a one-line summary annotation, so that site navigation does not crowd out main page content.
12. As an HTML schema author, I want purely decorative single-child `<div>` wrapper chains omitted and single-branch descendant paths collapsed inline with ` > ` (e.g., `h3 > a`), so that the DOM skeleton remains shallow and readable.
13. As an HTML schema author, I want each field in a repeating list archetype to display its presence coverage across items (e.g., `[24/24]` vs `[5/24, optional]`), so that I know immediately which fields require `fallback #null` in my KDL pipeline.
14. As an HTML schema author, I want each field in a repeating list archetype to show up to 3 distinct normalized text samples and key attribute samples (`href`, `src`, `content`, `value`, `data-*`), so that I can design string extraction, `re`, and type conversion (`to-int`, `to-float`) pipelines without extra probes.
15. As an HTML schema author, I want multiple same-tag/same-class siblings inside a single card that occur at a stable count (e.g., three `<span>` tags inside `.car-specs` for year, engine, and fuel) automatically split into separate `:nth-of-type(1)`, `:nth-of-type(2)`, and `:nth-of-type(3)` field rows with per-slot samples, so that I can see and select each distinct attribute of the item.
16. As an HTML schema author, I want same-tag/same-class siblings inside a single card whose count varies across items (e.g., 1 to 6 tag badges per card) reported as a nested array field with a `css-all` selector and `[array min..max items]` marker, so that I know to extract a `STR[]` list.
17. As an HTML schema author writing a `(table)struct` or `(dict)struct`, I want `scout` to detect both horizontal-header `<table>` elements (list candidates) and key-value `<table>` elements, `<dl><dt>/<dd>` lists, and repeating two-column label-value `<div>`/`<li>` rows, so that all specification blocks on a product or profile page are surfaced.
18. As an HTML schema author writing a `(table)struct`, I want key-value candidates to report verified `container`, `rows`, `key`, and `value` CSS selectors alongside the list of discovered keys and sample values, so that I can directly populate `@table`, `@rows`, `@match`, `@value`, and `match { ... }` field predicates.
19. As an HTML schema author using `jsonify`, I want `scout` to scan all `<script>` blocks using `json.JSONDecoder().raw_decode()` across multiple variable assignments (`var`/`let`/`const`/`window.X = ...`), `.push({...})` calls, and unescaped `JSON.parse("...")` strings, so that embedded strict JSON is discovered even when surrounded by JavaScript code or multiple assignments in one `<script>`.
20. As an HTML schema author using `jsonify`, I want `scout` to recursively traverse parsed embedded JSON payloads to locate deeply nested arrays of objects and large data dictionaries, reporting their exact GJSON path expressions (`path="props.pageProps.items"`), item counts, field names, inferred value types, and samples, so that I can write `jsonify Schema path="..."` and define the corresponding `json` schema in one step.
21. As an HTML schema author, I want trivial JSON objects inside scripts (fewer than 2 keys and no nested collections, such as `{"env": "prod"}`) filtered out of the embedded JSON report, so that noise does not obscure real data payloads.
22. As an HTML schema author, I want every JSON payload surfaced in the embedded JSON section to be guaranteed valid RFC 8259 JSON (parsed via standard `json` after any `JSON.parse` string unescaping), so that generated JSON projectors in Python, JavaScript, Go, and Rust never fail at runtime on loose JavaScript object literals.
23. As a user running `ssc-gen scout -i page.html --text "1 299"`, I want `--text` to match against normalized subtree text (including text split across child inline tags like `<span>1 299</span> <span>₽</span>`) and select the deepest minimal tag enclosing the match, so that inline formatting tags do not prevent text discovery.
24. As a user running `ssc-gen scout` with `--text`, `--attr`, `--tag`, or `--css` filters, I want the engine to automatically climb from matched leaf nodes to their enclosing repeating container, table, or semantic block and output that container's skeleton with `<-- MATCH` highlights on the matched nodes, so that I never have to manually guess `--up N` or `--next N` navigation steps.
25. As an LLM agent working within a strict context budget, I want default output limits (top 7 repeating lists, up to 25 fields per list, up to 3 samples of 80 chars per field, top 5 tables/KV blocks with up to 25 keys, top 5 JSON collections with up to 20 keys) applied automatically, and a `--full` flag available to bypass truncation when full page inspection is needed.
26. As a developer consuming reconnaissance results programmatically or in prompts, I want `-f text` (default) to emit a token-compact, human- and LLM-readable digest and `-f json` to emit a lossless JSON serialization of the same `ScoutResult` structure.

## Implementation Decisions

- **Single Public Reconnaissance Entrypoint (`run_scout` and `ScoutResult`)**:
  - Consolidate the exploration module around a single primary orchestration function `run_scout` and a unified result dataclass `ScoutResult` (with `.to_text()` and `.to_json()` serialization methods). Keep `run_discover` in the public facade only as a thin compatibility alias forwarding to `run_scout(html)` if needed by external imports, or unify the facade exports cleanly around `run_scout` and `ScoutResult`.
  - Remove legacy navigation/field-extraction types (`NavSpec`, `apply_navigation`, `extract_fields`, `DEFAULT_FIELDS`) that existed only for manual `--up`/`--down` and `--fields` table probing.
- **CLI Contract Simplification**:
  - Update `ssc-gen scout` options to:
    - `-i` / `--input`: HTML file path (reads from `stdin` when omitted).
    - `--css`: CSS selector filter for Zoom-in mode.
    - `--text`: Regex (or literal with `-F`) matched against normalized subtree text for Zoom-in mode.
    - `--attr`: Repeatable attribute filter (`NAME`, `NAME=VAL`, `NAME=~REGEX`) for Zoom-in mode.
    - `--tag`: Tag name filter for Zoom-in mode.
    - `-I` / `--ignore-case`: Case-insensitive regex matching.
    - `-F` / `--fixed`: Literal string matching (escapes regex metacharacters).
    - `--full`: Disable default output caps and render all discovered containers, fields, keys, and skeleton nodes.
    - `-f` / `--format`: `text` (default) or `json`.
    - `--discover`: Hidden/deprecated boolean flag accepted as a no-op so legacy invocations do not fail.
  - Exit codes remain: `0` when analysis succeeds (and at least one match is found when Zoom-in filters are active), `1` when Zoom-in filters are provided but match zero elements, and `2` on empty input or invalid CSS/regex filter syntax (`FilterError`).
- **DOM Preprocessing & Class Token Classifier**:
  - Parse HTML using the `lxml` BS4 parser engine. Before structural analysis (after extracting `<script>` tags for the Embedded JSON engine), strip `<svg>`, `<style>`, `<noscript>`, `<template>`, and HTML comments.
  - Classify class tokens on elements into three categories:
    1. *Autogenerated / Hash classes*: tokens matching common CSS-in-JS / bundler hash patterns (e.g., `css-[a-z0-9]{4,}`, `sc-[a-zA-Z0-9-]+`, `svelte-[a-z0-9]+`, `_+[a-zA-Z0-9]+_[a-z0-9]{4,}`, or tokens with high mixed-case/digit entropy).
    2. *Utility / State classes*: known Tailwind/Bootstrap layout, spacing, typography, flex/grid, responsive prefix (`sm:`, `md:`, `lg:`, `hover:`, `focus:`), and transient UI state tokens (`active`, `selected`, `disabled`, `open`, `hidden`, `first`, `last`, `odd`, `even`, `clearfix`, `container`, `row`, `col`, `col-*`, `flex`, `grid`, `block`, `inline`, `p-*`, `px-*`, `py-*`, `m-*`, `mx-*`, `my-*`, `text-*`, `bg-*`, `border-*`, `w-*`, `h-*`, `items-*`, `justify-*`, `gap-*`).
    3. *Semantic classes*: all remaining class tokens.
- **DOM-Verified Selector Synthesis**:
  - **Container / Item Selector**: Given a target list of $N$ item tags, prefer an ancestor `#id` or unique semantic anchor within $\le 3$ hops combined with the item's shared semantic class(es), `data-*`, `itemprop`, or tag name. Candidate selectors are tested with `soup.select(sel)`: a selector is accepted as `"stable"` if the selected element set equals the exact $N$ target items (by node identity), or if it selects all $N$ items within a unique parent container.
  - **Relative Field Selector**: Within a container item archetype, synthesize the shortest relative CSS selector from the item root to the field node (preferring unique semantic classes, `itemprop`, `data-*`, `name`, or tag path `h3 > a`), verified across the container's items so that `item.select_one(rel_sel)` (or `item.select(rel_sel)` for array/positional fields) resolves to the target descendant slot without colliding with unrelated nodes in the card.
- **Structural Clustering & Archetype Folding for Repeating Lists**:
  - Within each parent element (excluding `<head>`), group direct child tags into candidate repeating clusters:
    - Two children belong to the same cluster if they share the same `tag.name` AND either share at least one semantic class OR (when neither has distinct semantic classes) the Jaccard similarity of their descendant tag-name sets is $\ge 0.5$ (or both are leaf tags of the same name).
    - Clusters with $\ge 3$ items are promoted to repeating list candidates. Any remaining direct child siblings in the same parent with count $< 3$ that sit between cluster items are recorded as `outliers` (`tag.class`, count) on that container.
  - **Navigation Detection & Suppression**: A repeating cluster is flagged as `is_navigation = True` if it lies inside `<nav>`, `<header>`, or `<footer>`, or if every item is a bare `<a>` or wraps a single `<a>` with short text and no secondary data fields. In default mode, navigation clusters are rendered as one-line summaries rather than expanded into full field archetypes.
  - **Information Density Scoring**: Non-navigation clusters are scored and sorted descending by `score = count * (1 + 2 * unique_leaf_fields + text_diversity_bonus)` so data-rich lists always outrank repetitive boilerplate.
  - **Positional Slots vs Nested Array Disambiguation**:
    - When a relative `(parent_subpath, tag, semantic_classes)` signature occurs multiple times within a single item (`max_per_item > 1`):
      - If the occurrence count per item is consistent across $\ge 80\%$ of items containing that parent AND `max_per_item <= 6`, split the signature into separate positional field entries using `:nth-of-type(1)` .. `:nth-of-type(k)`, computing presence ratio and sample values independently for each slot.
      - Otherwise (variable count across items or $> 6$ items), emit a single nested array field entry with `is_array = True`, `css-all` selector, item count range `[min..max]`, and samples drawn across items.
  - **Inline Chain Collapsing**:
    - Pure layout wrapper nodes (`div`, `section`, `span` with a single child element, no direct text, and not required as a selector anchor) are elided in the rendered DOM skeleton, and single-child branches inside archetypes are formatted inline as `parent_seg > child_seg`.
- **Key-Value & Table Engine**:
  - Inspect `<table>` elements, `<dl>` elements, and repeating clusters whose items contain exactly 2 leaf text subtrees (or a label tag `strong`/`b`/`dt`/`label`/`th` paired with residual value text):
    - **`<table>` classification**: If a `<table>` has a `<thead>` (or first row of `<th>` cells) with $\ge 2$ columns and multiple data rows of `<td>` cells matching that column count, classify it as a `table_list` (surfacing column headers alongside column `:nth-of-type(k)` selectors) AND/OR if it is a 2-column table where column 1 holds short unique strings, classify it as a `kv_table` (candidate for `(table)struct` / `(dict)struct`).
    - **`<dl>` and 2-Column Repeating Rows**: When repeating rows have 2 sub-elements where the first element's text is short ($\le 50$ chars), non-numeric, and $\ge 80\%$ unique across rows in the block, classify the block as a `kv_block` (`(table)struct` / `(dict)struct` candidate) and emit verified `container_selector`, `rows_selector`, `key_selector`, `value_selector`, and up to 25 `(key, sample_value)` pairs.
- **Embedded JSON Engine (`raw_decode` + Deep Collection Discovery)**:
  - For each `<script>` tag and JSON-like HTML attribute:
    - Extract candidate JSON slices: full body for `application/ld+json` and `application/json`; unescaped string argument for `JSON.parse("...")`; and every `{` or `[` following `=`, `:`, or `.push(` in standard `<script>` blocks.
    - Parse each slice with `json.JSONDecoder().raw_decode()`. Ignore invalid slices and trivial objects (dicts with $< 2$ keys and no nested list/dict values).
    - Walk the parsed JSON value recursively (up to depth 8) to discover **Data Collections**:
      - Homogeneous arrays of objects (`list[dict]` with length $\ge 2$), recording their GJSON path expression from the root of the parsed JSON payload, array length, union of field keys (up to 20) with inferred KDL JSON primitive/container types (`str`, `int`, `float`, `bool`, `array`, `object`, plus `?` when null/missing in some elements), and 1–2 sample values per key.
      - Important root or nested data objects (`dict` with $\ge 3$ scalar/structured keys), recording their GJSON path expression, keys, inferred types, and sample values.
    - Emit the exact KDL extraction hint (`css "..."; raw inner; jsonify Schema` for typed scripts, `css "..."; attr "..."; unescape; jsonify Schema` for attributes, or `re "..."; jsonify Schema` for JS variable assignments / `JSON.parse`).
- **Zoom-in Filter & Auto-Container Expansion**:
  - When any of `--css`, `--text`, `--attr`, or `--tag` is supplied:
    - Evaluate candidate tags across the document. For `--text`, match the regex against `tag.get_text(" ", strip=True)`, then filter out any matching tag that has a descendant tag also matching the same pattern (retaining only the **deepest minimal matching tags**).
    - For each minimal matching tag, locate its enclosing semantic context: if it lies inside a discovered repeating list item or KV/table block, select that enclosing list/table container and mark the matched descendant field(s) with `matched = True` (`<-- MATCH`); otherwise climb up to 3 parent levels (stopping at `main`, `article`, `section`, or a tag with an `id` or semantic class) and build a detailed skeleton of that subtree with `<-- MATCH` on the target node(s).
- **Default Compression Budgets (when `--full` is False)**:
  - Max repeating list archetypes expanded: `7` (remaining lists summarized in 1 line each).
  - Max fields per repeating list archetype: `25`.
  - Max distinct sample values per field: `3` (truncated to `80` chars each, whitespace-normalized).
  - Max Key-Value / Table blocks: `5` (up to `25` keys each).
  - Max Embedded JSON signals/collections: `5` (up to `20` keys each).

## Testing Decisions

- **What Makes a Good Test**:
  - Tests must assert observable output semantics and domain contracts at the public boundary—never internal helper functions, regex constants, or private scoring formulas.
  - Every CSS selector emitted by `run_scout` in test assertions must be validated by running `soup.select(selector)` against the fixture HTML to prove that the synthesized selector is syntactically valid and matches the exact expected elements.
- **Seams to Test**:
  1. **Primary Seam — Public Python Facade (`run_scout(html, ...)` $\to$ `ScoutResult`, `.to_text()`, `.to_json()`)**:
     - Full-page overview distillation on complex HTML fixtures containing:
       - Repeating product/article cards where the count exceeds 5 (`N >= 6`, verifying the old `RARE_CLASS_MAX` bug is gone and the item class is preserved).
       - Cards with state/modifier classes on the first item (`class="card featured"`) and an inline outlier (`<div class="ad-banner">`) between cards.
       - Utility class soup (Tailwind/Bootstrap) and CSS-in-JS hash classes mixed with semantic classes.
       - Optional fields present on only a subset of cards (`[k/N, optional]`).
       - Same-tag siblings within a card: both fixed-count positional slots (`:nth-of-type(1..3)`) and variable-count badge arrays (`css-all`).
       - Navigation lists (`<nav>`, `<footer>`, single-link `<li><a>`) ranked below data-rich lists and collapsed into summary lines.
       - Key-value blocks across all three representations: `<table>`, `<dl><dt>/<dd>`, and repeating two-column `<div>`/`<li>` label-value rows.
       - Embedded JSON across `<script type="application/ld+json">`, `<script id="__NEXT_DATA__" type="application/json">`, multiple `window.X = {...}; window.Y = [...];` assignments in a single `<script>`, `JSON.parse("...")` wrappers, and deeply nested object arrays yielding GJSON path expressions.
     - Zoom-in mode (`text`, `attr`, `tag`, `css`, `ignore_case`, `fixed`):
       - Text matching across inline child tags (e.g., `<div>Price: <span>$19.99</span></div>`) selecting the minimal enclosing node.
       - Automatic container expansion to the enclosing repeating list or KV block with `<-- MATCH` highlighting on the matched field.
     - `--full` mode lifting truncation limits.
  2. **Secondary Seam — CLI Entrypoint (`CliRunner` on `ssc-gen scout`)**:
     - File (`-i`) and `stdin` input handling.
     - Default text output vs `-f json` valid JSON output.
     - `--discover` accepted silently as a deprecated alias.
     - Exit codes: `0` on match/overview, `1` on zero matches in Zoom-in mode, `2` on empty HTML or invalid regex/CSS selector.
- **Prior Art in the Codebase**:
  - Existing exploration unit tests and integration HTML fixture tests in the test suite. Legacy tests asserting on removed navigation helpers (`NavSpec`, `apply_navigation`) or legacy `DiscoverResult` keys will be replaced with tests targeting the new `run_scout` contract.

## Out of Scope

- Adding external C-extension dependencies such as `chompjs` for parsing non-standard JavaScript object literals (all surfaced JSON signals must remain valid RFC 8259 JSON compatible with `jsonify` and generated target JSON projectors).
- Executing headless browsers or JavaScript runtimes to render client-side-only SPAs.
- Automatically generating complete `.kdl` files directly from `ssc-gen scout` (the tool prepares structured context and verified selectors for an LLM or developer to author the `.kdl` schema; `ssc-gen json-to-kdl` remains the dedicated generator for JSON schemas).
- Modifying KDL Schema DSL syntax, compiler passes, or target code generators (`PythonVisitor`, `JsVisitor`, `GoVisitor`, `RustVisitor`).
