# План реализации Rust-target

Статус: согласован. Открытых вопросов по требованиям первой версии нет.
Реализация ещё не начата. Технические решения, требующие проверки компиляцией,
выделены в этап прототипирования.

## 1. Согласованный объём

- Новый target существующего Python-кодогенератора: KDL → общий AST → Rust.
- Первая версия: HTML- и raw-схемы, включая `@init`, `@check`,
  `@pre-validate`, `nested`, fallback, JSON pipeline и пользовательские extensions.
- HTML-backend: `dom_query`; CSS-only, без внешних C-библиотек.
- XPath-операции и XPath-предикаты отклоняются при генерации Rust.
- Регулярные выражения: Rust `regex`, без lookaround и обратных ссылок в шаблоне.
- JSON: `serde` + `serde_json`, типизированные результаты.
- Результат генерации: `.rs`-модули для существующего Cargo-проекта.
- Общий соседний модуль `sscgen_runtime.rs`; импорт через
  `super::sscgen_runtime` позволяет вложить весь набор в пользовательский модуль.
- HTML `@request` и REST — последующие этапы. В первой версии используемые
  неподдержанные конструкции дают явную ошибку генерации.

## 2. Поведение удалённого кешированного узла

Сценарий: `@init` сохраняет узел; другая операция удаляет его через
`css-remove`; дальнейшая операция читает тот же узел через `@name`.

Согласованное поведение:

- Удаление отсоединяет узел от дерева. Кешированная ссылка продолжает
  обозначать тот же узел, его содержимое остаётся доступно.
- Новые выборки от корня его не находят. Выборки относительно сохранённого
  узла работают в его текущем, отсоединённом контексте.
- Кешированная коллекция сохраняет выбранный состав; это не повторный запрос.
- Это ссылка на живой узел, а не снимок: дальнейшие изменения через другие
  ссылки на этот узел видны при чтении.
- Отсоединённые узлы удерживаются деревом до освобождения владельца документа.

Такое поведение соответствует модели `dom_query` и сохраняет идентичность
узлов в предварительных вычислениях, вложенных парсерах и расширениях.

## 3. Публичный API и жизненный цикл

```rust
let product = ProductParser::new(html)?.parse()?;

let mut parser = ProductParser::new(html)?;
let first = parser.parse()?;
let second = parser.parse()?;
```

- `new(...) -> Result<Self, SscError>` подготавливает вход, затем выполняет
  все `@init` pipeline в порядке объявления, включая неиспользуемые в выходе.
- `@init` значения принадлежат экземпляру. Ссылки `@name` читают кеш;
  предварительные вычисления не становятся автоматически выходными полями.
- `parse(&mut self) -> Result<Output, SscError>` при каждом вызове выполняет
  `@pre-validate`, затем разделение документа и извлечение полей.
- Повторный `parse()` сохраняет кеш `@init` и накопленные изменения DOM.
- Именованные `@check` — публичные методы с результатом
  `Result<bool, SscError>`; проверка не получает неявный `fallback #false`.
- `nested` создаёт дочерний экземпляр, выполняет его `@init` и вызывает
  `parse()`. Вложенный HTML-парсер работает с тем же деревом.
- Результат владеет данными: строки, коллекции, JSON- и вложенные модели
  могут пережить экземпляр парсера и его DOM.
- Raw-парсеры используют тот же жизненный цикл, начиная со строки.

### Ошибки и side effects

- Ошибки извлечения, приведения, индексации, assertions, JSON и extensions
  возвращаются через `SscError` с контекстом структуры, поля/инициализатора
  и операции. Публичный тип ошибок общий для набора модулей.
- Fallback восстанавливается после ошибок охваченного pipeline;
  `fallback #null` даёт `Option<T>` для поддержанных DSL типов.
- Выполненные DOM-изменения сохраняются при ошибке и после fallback.
- Штатные ошибки данных не реализуются через panic; fallback не использует
  `catch_unwind` для перехвата паник расширений.
- Исправимые HTML parse diagnostics сами по себе не делают tolerant HTML
  parsing ошибкой. Ошибки `@init` остаются ошибками конструктора.

## 4. JSON-контракт

Порядок: разобрать JSON → выбрать `path` → применить объявленную схему
к выбранному фрагменту → получить типизированный результат.

Имя схемы описывает выбранный фрагмент, а не содержащую его оболочку.
Кардинальность определяется объявлением:

```kdl
json Product {
    id int
}

(array)json Products {
    id int
}

(raw)struct Response {
    one { jsonify Product path="data.products.0" }
    many { jsonify Products path="data.products" }
}
```

Здесь `one` получает модель `ProductJson`, а `many` —
`Vec<ProductsJson>`. Суффикс `Foo[]` у аргумента `jsonify` не является
существующим синтаксисом модификатора массива.

| Поле | Отсутствующий ключ или `null` | Непустое значение неверного типа |
|---|---|---|
| Обязательное `T` | Ошибка | Ошибка |
| Nullable `T?` | `None`, сериализация как `null` | Ошибка |
| Под действием `@omitempty` | `None`, ключ пропускается при сериализации | Ошибка |

- `0`, `false`, пустые строки и массивы сохраняются.
- `from="..."` выбирает путь во входном JSON; сериализация использует
  каноническое имя DSL. `@skip` исключает поле из результата.
- Пути по полям и массивам обрабатываются отдельно от Serde rename-атрибутов.
- Проекция включает объявленные поля; Serde проверяет типы выбранных значений.
- Строгая проверка значений — согласованное отличие от permissive projection
  существующих Python/JS target.
- Существующие JSON-пути сохраняют свою грамматику. Отрицательная индексация
  строк/массивов в pipeline не добавляет её автоматически в JSON-пути.

### Необходимое согласование общего AST

В текущем `resolve_jsonify_type` путь ошибочно интерпретируется как путь
через именованную схему. Нужно:

1. В `core/expressions.py` вычислять тип из указанной `JsonDef`:
   `base=JSON`, `is_array=json_def.is_array`, `ref=schema_name`.
2. Устранить принудительное scalar-приведение `jsonify` в
   `core/type_checking.py`; сохранить полную информацию о типе.
3. Проверить распространение типа в `Return`, fields, `@init` и output typedefs.
4. Исправить противоречащие fragment-first контракту примеры `docs/json.md`.
5. Проверить существующие Python/JS/Go consumers исправленного AST.

REST не вызывает `resolve_jsonify_type`: его кардинальность берётся отдельно
из `JsonDef`. При изменении общих projection helpers нужны REST-регрессии.
ADR-0001 описывает прежний permissive remapping Python/JS; Rust-строгость
нужно документировать отдельно, не выдавая её за уже общий контракт.

## 5. Операции и совместимость

- CSS: выборки, удаление, DOM-предикаты. Матрица поддержанных селекторов
  проверяется на `dom_query`; отсутствие XPath диагностируется явно.
- `text`: текст потомков без неявного trim; обработка пробелов — явные
  операции DSL. Для коллекций — извлечение отдельно из каждого узла.
- `raw`: сериализация узла/его содержимого согласно варианту операции;
  проверить outer/inner HTML и изменения DOM, а не возвращать исходный HTML.
- Строковые длины/индексы — Unicode scalar values, как Python для корректного
  Unicode; не байты UTF-8 и не графемные кластеры.
- Отрицательные индексы поддерживаются; одиночный выход за границы — ошибка;
  slice полуоткрытый, с обрезанием границ.
- `regex`: единый контракт для извлечения, замен и всех regex-предикатов.
  Подстановки DSL переводятся в Rust-синтаксис с корректным экранированием.
- Текущий lint через Python `re.compile` пропускает lookaround/backreferences;
  требуется проверка совместимости Rust-target, а не доверие общему lint.
- `extension`: ключ `rust`, imports/helpers, существующие placeholders типов
  и значений; `?` разрешён в fallible pipeline. Использованное расширение без
  Rust-реализации — ошибка генерации.

## 6. Предлагаемая внутренняя структура

```text
ssc_codegen/targets/rust/
    __init__.py
    visitor.py       # явные visit_* endpoints, RustVisitor(BaseWalker)
    dom.py           # dom_query-specific spelling
    runtime.py       # исходники общих Rust helpers и их сборка
    regex.py         # совместимость шаблонов, флагов и замен
```

Дополнительные модули выделяются по содержательным обязанностям по мере
реализации, без копирования всего Python/Go visitor и без forwarding-only слоёв.

- `BaseWalker` и `WalkContext` сохраняют роль обхода; target использует
  `ModuleBuilder` для накопления импортов и helpers в двухпроходной генерации.
- Для owned-парсера с DOM-кешами прототипировать общий владелец документа
  плюс root/cached node IDs. Временные `NodeRef`/selection создаются при работе
  с деревом; self-referential struct и сериализация/reparse для `nested`
  не требуются.
- Конкретное представление handles проверить компиляцией до реализации
  остальных visitor handlers. Внутренний вход от handle нужен для `nested`.
- Выборки материализуются до мутационно способного обхода; lazy iterator
  `dom_query` нельзя сохранять через изменение дерева.
- Повторное чтение owned-значения `@init` использует заимствование или clone,
  не перемещает значение из экземпляра при первом `parse()`.
- Runtime аккумулирует helpers всех входных модулей перед финальной записью.
  Модели результатов остаются локальными сгенерированному модулю.
- Версии crates/features, Rust edition и минимальную версию Rust зафиксировать
  по результатам компилируемого прототипа на stable toolchain.

## 7. Этапы реализации

### Этап 1. Устранить неоднозначности типов и закрепить контракты

- Добавить регрессии fragment-first `jsonify`: object/array, envelope paths,
  init values, nested models и типы результатов.
- Исправить перечисленные seams общего AST/type checker.
- Проверить сообщение `fallback #null` → optional metadata; исправить
  обнаруженные разрывы распространения типа в рамках уже допустимого DSL.

Готово, когда AST несёт достаточно информации для корректных Rust типов,
а затронутые существующие target проходят регрессионные проверки.

### Этап 2. Компилируемый DOM/runtime прототип

- Зафиксировать dependencies: `dom_query`, `regex`, `serde`, `serde_json`.
- Проверить владение документом и кешированными узлами, repeated parse,
  `nested`, удаление и fallible constructor на минимальном Rust-примере.
- Зафиксировать `SscError`, DOM handle contract, типы примитивов и visibility.
- Проверить Unicode helpers и строгую Serde-модель с alias/path/omitempty.

Готово, когда выбранное представление компилируется и демонстрирует весь
согласованный жизненный цикл без обхода ownership через unsafe.

### Этап 3. Первый вертикальный срез генерации

- Добавить `RustVisitor`, профиль/resolver и явную CLI-команду
  `ssc-gen generate rust ...`.
- Реализовать item/raw parser, типизированный output, `new`, `parse`,
  простые CSS/text/attr/cast pipeline и общий runtime.
- Генерировать по KDL, собирать в Cargo-fixture, исполнять и проверять данные.
- Сразу диагностировать неподдержанные узлы; технические AST no-op
  обработчики отделить от отсутствующих реализаций.

### Этап 4. Полное покрытие согласованной первой версии

- `@init`, ссылки на кеш, public checks, pre-validation, `nested`.
- Все объявленные HTML/raw struct shapes: item/list/dict/flat/table/raw.
- Строки, массивы, casts, regex, filter/assert/match, логические и DOM-предикаты.
- Fallback, optional results, таблицы и пропуски unmatched rows.
- JSON-декларации, fragment selection, projection и Serde types.
- `rust` extensions; обновить независимые списки языков в
  `core/extensions.py` и `core/linter.py`.

### Этап 5. Многомодульная сборка и документация

- Проверить объединение runtime helpers, конфликты имён, KDL import closure,
  Rust identifiers/keywords и несколько схем в одном родительском модуле.
- Добавить пример `mod`-подключения и точный Cargo dependency fragment.
- Описать поддержанные возможности, ошибки, side effects и JSON-контракт.
- Обновить maintainer/LLM references для нового target.

## 8. Проверки и критерии приёмки

Проверки поведения сгенерированного кода выполняются через Cargo-fixtures,
оркестрируемые pytest (`tests/rust/test_rust_codegen.py`). Сравнение текста
генерации дополняет, но не заменяет компиляцию и выполнение.

- Форматирование: `cargo fmt --check`.
- Сборка и исполнение: `cargo check`, `cargo test`.
- Python-часть: `uv run pytest` для затронутых suites, затем общий набор
  после изменений shared core; `uv run ruff check ssc_codegen/ tests/`;
  `uv run mypy ssc_codegen/`.
- CI с обязательным Rust toolchain проверяет Rust fixtures на Windows/Linux;
  локальное отсутствие Cargo должно обозначаться явно в результатах проверок.

Обязательные сценарии:

1. `new` вычисляет init ровно один раз, в порядке объявления; ошибка init
   выходит из конструктора, а не из первого parse.
2. `parse` повторяем, checks публичны, nested выполняет собственный init.
3. Изменения DOM видны последующим полям и сохраняются после fallback;
   кешированный удалённый узел проверяется по согласованному контракту § 2.
4. Выходные данные живут после освобождения парсера.
5. Missing single selector/attribute, неверный cast/index, regex no-match,
   assert и JSON type mismatch дают ожидаемый `SscError`; fallback их ловит.
6. Unicode, отрицательные индексы и границы slice проверяются на кириллице,
   emoji, пустых строках и массивах.
7. JSON object/array fragments, `from` paths, optional/omitempty/skip,
   aliases и канонические имена при сериализации проверяются исполнением.
8. Regex-флаги, capture groups и replacement escaping проверяются вместе
   с явным отклонением неподдержанных конструкций.
9. Rust extensions проверяются с `?`, helpers, imports, type placeholders
   и повторным использованием кешированных значений.
10. Несколько parser modules и единый runtime компилируются как вложенный
    модуль пользовательского crate без конфликтов имён и типов ошибок.
11. XPath, HTTP/REST и отсутствующая Rust-реализация используемого extension
    завершаются понятной диагностикой генерации.

Готовность target означает покрытие согласованной матрицы операций,
успешную компиляцию и ожидаемое поведение fixtures, а не только наличие
`visit_*` методов. Известные различия текущих target не становятся эталоном
автоматически: приоритет у согласованных контрактов этого плана.
